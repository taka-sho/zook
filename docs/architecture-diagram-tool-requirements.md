# アーキテクチャ図生成ツール 要求仕様書

**バージョン:** 0.1（要求分析フェーズ）
**作成日:** 2026-07-25
**ステータス:** ドラフト / 詳細要件定義への入力用

---

## 1. 概要

YAML で記述したクラウドアーキテクチャ定義から、PowerPoint（.pptx）スライドを自動生成するツールを新規開発する。図はコードベース（Git）で管理し、差分を明確に追える状態を保つ。将来的には LLM がYAMLを生成し、要件を渡すだけで図が出てくる「半自動生成」を想定する。

## 2. 背景・課題

- 既存の diagram-as-code ツール（awsdac 等）は「コードで管理」「AWSアイコン」「自動レイアウト」までは満たすが、**アスペクト比の厳密な指定**と**PowerPoint 直接出力**に制約がある。
- 変換スクリプトを噛ませる運用は毎回妥協が発生し、メンテナンスコストが高い。
- 日本企業（JTC）の実務では、見た目の美しさよりも「PowerPoint での取り回し」「情報の詰め込みやすさ」「再現性・メンテナンス性」が重視される。
- 最終成果物は PowerPoint で人間が手編集する前提のため、完璧な自動レイアウトよりも「編集の起点として十分な図」が出ればよい。

## 3. 目的

YAML 入力から PowerPoint 出力までを一本化したパイプラインを構築し、以下を実現する。

- アーキテクチャ図をコードとして Git 管理し、差分をレビュー可能にする。
- PowerPoint への出力を標準機能とし、人間による後編集を前提とする。
- LLM による YAML 自動生成を見据えた、機械可読・曖昧さの少ない仕様とする。

## 4. スコープ

### 4.1 対象（第一版）

- 入力フォーマット: **YAML**
- 出力フォーマット: **PowerPoint（.pptx）**
- 対応プロバイダ: **AWS**（主要サービスから開始）
- 対応サービス（初期）: Lambda / EC2 / RDS / S3
- 構成要素: VPC（四角で囲む表現）、複数アベイラビリティゾーン（AZ）
- 生成単位: **1 YAML = 1 スライド**

### 4.2 対象外（第一版では扱わない）

- 大量バッチ生成（1回で数十枚以上の生成は想定しない）
- 実クラウドリソースの作成・操作（IaC 機能は持たない。描画専用）
- 完全自動の美麗レイアウト（後編集前提のため過剰な最適化はしない）

## 5. ユーザーペルソナ・ユースケース

| ペルソナ | 主なユースケース |
|---|---|
| PM / 営業 | 提案業務で顧客向けに構成図（架空図含む）を作成する |
| SRE / インフラエンジニア | 社内インフラ変更時に構成図を更新・共有する |
| アーキテクト | 設計時のアーキテクチャ図をコードで管理する |

- 幅広い職種が利用する想定。専門知識が浅いユーザーも含む。
- 実運用ではLLMがYAMLを生成する形を主とし、ユーザーは要件を渡す・微修正する役割が中心になる。

## 6. 使用頻度・規模

- 頻度: 週1回 〜 月2回程度。
- 1回あたりの生成枚数: 少数（大量生成は非対象）。
- 性能要件は緩め。1枚の生成に多少時間がかかっても許容。

## 7. 機能要件

### 7.1 入力（YAML）

- R-IN-01: アーキテクチャ構成を YAML で定義できること。
- R-IN-02: VPC を定義し、その内部に複数のサービスを配置できること。
- R-IN-03: 複数の AZ を定義し、サービスをいずれかの AZ に割り当てられること。
- R-IN-04: 各サービスにタイプ（EC2 等）と表示名を指定できること。
- R-IN-05: 各要素に位置（X, Y 座標）とサイズを任意で指定できること。
- R-IN-06: 位置を指定しない要素は、自動的に整列・配置されること（後述 §10）。
- R-IN-07: サービス間の関係（リンク）を定義できること（後述 §11）。
- R-IN-08: 人間可読性よりも、機械（LLM）が曖昧さなく生成・パースできることを優先した構造とする。

### 7.2 出力（PowerPoint）

- R-OUT-01: YAML 1ファイルから 1スライドの .pptx を生成すること。
- R-OUT-02: スライドのアスペクト比（16:9 / 4:3 等）を指定できること。
- R-OUT-03: 生成される図要素は、PowerPoint 上で人間が選択・移動・編集できる形（可能な限りネイティブ図形／画像）で配置すること。
- R-OUT-04: AWS 公式の PowerPoint テンプレート／アイコン体系を参考にした見た目とすること。
- R-OUT-05: 情報を詰め込めること（ラベル・注釈などを要素に付与可能）を優先し、余白最適化は控えめでよい。

### 7.3 描画要素

- R-DR-01: VPC を四角（枠）で表現し、内部に子要素を内包できること。
- R-DR-02: AZ を VPC 内のグループとして表現できること（入れ子構造）。
- R-DR-03: サービスをアイコン＋ラベルで表現できること。
- R-DR-04: アイコンの表示サイズを指定できること。
- R-DR-05: 関係性を「矢印（接続線）で結ぶ」パターンと、「線を引かずグループ／エリア内に配置するだけ」のパターンの両方に対応すること。

### 7.4 アイコン・プロバイダ

- R-IC-01: 初期は AWS 主要サービス（Lambda / EC2 / RDS / S3）に対応すること。
- R-IC-02: AWS 公式 SVG アイコンを利用すること。
- R-IC-03: アイコンを外部フォルダから参照できる仕組みとし、プロバイダ（AWS / GCP / Azure 等）やカスタムアイコンを追加しやすい設計とすること（例: `icons/aws/`, `icons/gcp/`, `icons/custom/`）。
- R-IC-04: 特定クラウドに限定せず、任意のアイコン画像を配置できる汎用性を持つこと。

### 7.5 運用・CI/CD

- R-OP-01: YAML を Git で管理し、変更差分がレビューできること。
- R-OP-02: YAML → PPTX 出力を実行する CLI コマンドを提供すること。
- R-OP-03: CI/CD パイプラインから当該コマンドを呼び出し、インフラ変更に合わせて図を再生成できること。

## 8. 非機能要件

- R-NF-01（保守性）: プロバイダ・アイコンの追加が、コア実装の改修なしに行えること。
- R-NF-02（機械可読性）: YAML スキーマを JSON Schema 等で形式定義し、LLM の誤生成を減らせること。
- R-NF-03（品質）: 出力図は「そこそこきれい」であればよく、最終調整は PowerPoint 上の手編集で行う前提とする。
- R-NF-04（移植性）: 特定OS・特定GUIに依存せず、CLI 単体で動作すること（CI/CD で動かせること）。
- R-NF-05（拡張性）: 将来的に MCP サーバー化し、Claude 等の LLM から直接呼び出せる構成を見据えること。

## 9. 入力仕様（YAML）の方向性

- ルートに図全体の設定（キャンバスサイズ / アスペクト比）を持つ。
- VPC → AZ → サービス という階層（Children）で内包関係を表現する。
- 各要素は任意で `x` / `y` / `size` を持ち、指定がなければ自動配置。
- リンクは要素間の参照（from / to）で表現し、ラベルを任意で付与できる。
- ※ 具体的なフィールド名・スキーマ確定は詳細要件定義フェーズで行う。以下は構造イメージ（確定版ではない）。

```yaml
version: "1.0"
canvas:
  aspectRatio: "16:9"      # 16:9 / 4:3 等
vpcs:
  - name: "MyVPC"
    availabilityZones:
      - name: "AZ-A"
        children:
          - type: "EC2"
            name: "WebServer"
            # x / y / size は任意。無ければ自動配置
          - type: "RDS"
            name: "Database"
      - name: "AZ-B"
        children:
          - type: "Lambda"
            name: "Worker"
links:
  - from: "WebServer"
    to: "Database"
    label: "3306"          # 任意。線を引かない構成も許容
```

## 10. 位置・レイアウト仕様の方向性

- 位置未指定の要素は、コンテナ（VPC / AZ）内で自動的に整列・配置される。
- `x` / `y` を指定した要素は、絶対位置で配置される。
- 自動配置と絶対指定は混在可能とする（一部だけ座標指定、残りは自動）。
- レイアウトの厳密な美しさより、後編集の起点として妥当な配置を優先する。

## 11. 関係性・リンク仕様の方向性

- サービス間を矢印（接続線）で結べること。
- 線にラベル（ポート番号・プロトコル等）を任意で付与できること。
- 線を引かず、単にグループ／エリア内にアイコンを配置するだけの表現も選べること。

## 12. 将来拡張

- MCP サーバー化により、Claude 等の LLM から「要件を渡す → YAML 生成 → 図出力」を半自動で実行する。
- そのために、YAML スキーマと生成ルールを **AI 向けの仕様書**として整備しておく。
- マルチクラウド（GCP / Azure）および任意アイコン参照へ段階的に拡張する。

## 13. 制約・前提

- 描画専用ツールであり、実インフラの構築・変更は行わない。
- 最終成果物は PowerPoint で人間が手編集する前提。
- 初期対応サービスは AWS の Lambda / EC2 / RDS / S3 に限定。

## 14. 未決事項（詳細要件定義で確定する）

1. YAML スキーマの正式定義（フィールド名・必須/任意・enum・型）。JSON Schema 化の要否。
2. アスペクト比指定時の挙動（レターボックス／引き伸ばし／自動調整）。
3. PowerPoint 上の図要素をネイティブ図形にするか画像埋め込みにするか（後編集のしやすさとのトレードオフ）。
4. AZ・VPC の入れ子表現の描画ルール（枠色・背景色・ラベル位置）。
5. 自動レイアウトのアルゴリズム（単純グリッド整列で足りるか）。
6. CLI の引数仕様、CI/CD への組み込み方法。
7. 実装言語・主要ライブラリ（例: Python + python-pptx を想定しているが確定は詳細フェーズ）。
