# 既知の制約(v1)

archdiagram は「PowerPoint 手編集の起点として十分な図」を目標としており、完全自動の美麗レイアウトは目指していません。v1 時点での既知の制約は以下の通りです。

## 重なりは検出のみ、自動回避はしない

座標未指定の要素は grid/horizontal/vertical で自動整列されますが、既に座標指定された兄弟要素を避ける処理は行いません(第一版仕様)。生成後、計算済みの座標から次の2種類の重なりを機械的に検出して Warning を出しますが、位置をずらす・迂回させるなどの自動修正はしません。

- 兄弟要素同士の矩形の重なり(親子関係にある要素同士は対象外)
- リンク(矢印)の経路が接続先以外の要素、または他リンクのラベルを横切っている場合

一方で、「ノードの位置がたまたま無関係なリンクのラベルの上に乗っている」ような、要素とリンクラベルの重なり単体は検出対象外です(リンクの経路自体がその要素を横切っている場合のみ検出されます)。いずれも生成後に PowerPoint 上で位置調整することを前提としています。

## リンク経路検知は直線近似

リンク経路の重なり検知は、コネクタの接続点座標を結ぶ線分をもとに判定します。`style: straight`(既定)であれば実際の描画結果と完全に一致しますが、`elbow`(直角に折れる線)・`curved`(曲線)は実際の折れ方・曲がり方まで再現していないため、直線で近似した参考値になります。折れ線・曲線が直線近似と大きく異なるルートを取る場合、見逃しや誤検知が起こり得ます。

## コネクタは矩形図形限定

接続対象(アイコン画像・コンテナ枠)はすべて矩形として扱われます。python-pptx のコネクタ実装自体が矩形以外では安定動作を保証していないためです。

## コネクタラベルは移動に追従しない

OOXML スキーマ上の制約により、リンクラベルは独立したテキストボックスとして中点に配置されます。生成後に図形を大きく動かした場合、ラベル位置は追従しません(詳細は[内部設計メモ](design-notes.md#connector-labels))。

## アイコンはプレースホルダー

同梱のアイコン画像は AWS 公式アイコンではなく、自作のプレースホルダーです。実運用では [アイコン・レジストリ](icons.md#icon-assets) の説明に従い、公式アセットに差し替えることを想定しています。

## マルチクラウド未対応

YAML スキーマ・レジストリ形式自体は `provider` によるマルチクラウド拡張を見据えていますが、v1 で組み込みレジストリが用意されているのは AWS のみです。GCP/Azure 用レジストリの追加は次版スコープです。

## 大量バッチ生成は想定外

1回の実行で数十枚以上のスライドを生成するような用途は想定していません(1 YAML = 1 スライド、週1〜月2回程度の利用を想定)。
